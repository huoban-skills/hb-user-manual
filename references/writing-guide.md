# 写作规范

## 一、整体结构

文档只有一种结构单元：**章节**。一个章节讲一个业务动作或场景；多个章节套上册头就是模块手册，只有一个章节就直接成篇。

### 章节骨架

```
## 一、章节名

场景介绍：是什么、为什么、怎么做的简要概括（不加"业务定位"标题）

### 1.1 开始前                ← 可选：权限、要先建好的资料；没有不写
### 1.2 操作名                ← 三级标题必须编号；多个操作依次排
### 1.x 字段说明              ← 可选，写不写在定骨架时让用户定
### 1.x 注意事项              ← 必有
### 1.x 常见问题              ← 必有，不许只在文末放全局的
```

- **字段说明和审批说明是章节内的可选件**，定骨架时让用户定要不要。审批不占独立小节，作为业务动作的环节写进步骤（见「审批流程」）。
- 一个章节只讲一件事，藏着两件事就拆两章/两篇。

### 单章成篇

只有一个章节时不套册头：不写模块名、不写模块场景介绍，章节自己就是整篇。

- 标题用读者要做的事命名（"如何配置到期提醒"），不用功能名（"提醒功能说明"）；场景介绍写适用场景（什么时候需要做、做完能得到什么）。
- 面向平台通用读者的篇目不预设某个工作区的业务背景，举例用通用业务场景。

### 成册编排（多章时）

- 册头：`# 模块名`（不追加"使用手册"）+ 模块场景介绍。
- 两个**册级可选章**，定骨架时让用户定要不要：
  - 「通用操作」：放在正文章节之前，把所有表共有的操作（创建记录、导入、视图筛选、批量修改等）写一次，后面各章不再重复。
  - 「典型业务场景」：放在册末，写法见下节。
- 模块类型三选一，决定章节单位。不要把业务流程模块写成单表手册：
  - **基础资料/数据维护**：一章一表，按依赖排序，被依赖的在前；册头可加"建议维护顺序""表间关系总览"两节。
  - **业务流程**：一章一个业务闭环，如销售报价、订单、发货、收款。
  - **混合**：以业务流程为主，资料表集中放第一章；资料表少且简单时可并入相关业务章节。

### 章节归属

- 主单据和明细表构成同一业务动作时不拆两章；明细表有独立业务含义才单独成章。
- 入口不决定归属：按钮在订单表上，不代表内容写进订单章；本身是独立业务闭环（如销售退货）就单独成章，步骤里说明从哪发起。
- 主-明细表族（如工艺+工艺路线）在同一大章下用子标题组织，介绍讲清表间关系（"工艺是目录，工艺路线是正文"）。
- 每个场景只写在它所属的模块手册里（建档归基础资料，对账核销归应收/应付）；不属于本模块的操作用引导语带过，且必须补半句业务缘由：
  - ✅ "采购入库确认后，对账付款要到「应付管理」继续，只有在那里核销这笔采购才算财务结清，详见对应手册。"
  - ❌ "供应商对账、付款录入属于「应付管理」模块，详见对应手册。"
- 章节内可加"开始前"小节写前置条件（要先建好什么资料、需要什么权限），没有就不写。

### 步骤写法

- 格式：先用一句话说场景，再接编号步骤。只有一个场景时场景句加粗即可，不加"操作场景"标题。
- 步骤动词开头；关键步骤后跟一句系统的预期反馈（"保存后列表里出现这条记录，状态为草稿"）；结果融入最后一步。
- 禁止"触发时机/操作步骤/操作结果"三段式。

### 字段表

格式 `| 字段 | 填写方式 | 是否必填 | 说明 |`，不拆"手动/自动"两组表，填写方式列区分 `手动填写` / `系统自动`。

- 顺序对齐表单主区布局（form-layout 的 main_layout），和操作者看到的表单一致。
- 说明列写法：
  - 显示条件字段：写清出现条件（"出库类型选「销售出库」后才显示"）。
  - 计算字段：不贴公式，用业务语言讲逻辑（"订单总金额减已收款金额，系统自动算，不用手填"）。
  - 自动编号：写清单号构成（"DD + 年月日 + 3位流水，每天从001重计"）。
  - 默认值：标注（"新建时默认今天""从订单发起时自动填「退货入库」，无需修改"）。
  - 关联字段标 `→ 目标表名`；关联附加字段填写方式写 `系统自动`，说明"从XX表自动带入，仅供查看"。
- 流程状态、流程发起人等平台过程字段不写；订单状态、待收款总额等业务判断字段要写。

### 审批流程

- 作为业务动作的一个环节写进对应章节（"提交后进入采购审批"），不单开大章、不画流程图。
- 写清三件事：什么时候触发、谁来审（环节名，写岗位不写姓名）、通过和驳回后系统分别会怎样（"审批通过后采购状态自动变为待入库"）。
- 未启用的流程不写；环节没采集到标 `[待确认]`，不编。

### 典型业务场景（成册可选章）

单章教会读者一个动作，这一章教会读者把几个动作串成一件事，专治"每张表都会用、业务串不起来"。

- 每个场景用一线员工的真实问法开头："跟供应商约定每月 5 号付未结货款，怎么处理？"，不用归纳式标题。
- 步骤跨章串联：只写串联点（在哪张表做什么、状态怎么流转到下一步），单步细节引用对应章节，不重复。
- 场景来自用户提供或实测观察到的真实业务，不为覆盖功能强行编。

### 注意事项写法

- 不止提醒，要写实测到的**系统硬边界**：什么情况下按钮置灰或操作不允许、改这里会联动改哪里、删除后能不能恢复。来源是实测或配置，不编。
- 操作性提醒（易填错、易点错的）照写。

### 外部平台的出处

跨平台内容里，凡是**来自外部平台的东西都要给出处**，两类都算：

- 要填的值（ID、密钥、回调地址）：给获取页面链接 + 获取步骤的分步截图，不许只写"填入XX即可"。
- 要照抄的规格（请求体格式、参数、频率上限）：给对方官方文档链接并说清是谁定的规矩。链接要实际打开核过，不能凭印象写。
- 特别注意从演示环境里读出来的配置：它是实测所得，但**规格的出处仍然在外部平台**，照抄进文档一样要给官方链接。

## 二、语言与例子

- 面向一线操作人员，像跟同事解释，不要说明书腔调。
- 禁止技术术语（validator、trigger、automation、config、API 等）："数据触发自动xxx"→"系统会自动xxx"；"validator 校验"→"保存时系统会自动检查，xxx时弹窗提示"。
- 界面名词用平台/系统原名，不转述不生造。
- 损耗率、转化率这类不直观的概念，用 `>` 引用块配具体例子。例子贴读者行业，给到能照着填的具体值（"1 包=3 个，1 箱=15 个"），不停留在"如某商品"；拿不准标 `[待确认]`。
- **不吹功能**：删掉"强大""高效""极大提升"这类形容词，价值用具体业务结果说（✅"少录一遍数据" ❌"大幅提升录入效率"）。
- **收尾即停**：写完最后一步就结束，不加"配置完成后，您的团队协作将更加顺畅"式展望，也不写"希望本文对你有帮助"。
- **句式不套路**：不硬凑"不仅…还…""从…到…"和三个一组的排比；破折号不用，断句或用冒号。
- **废话压缩**："具有导出能力"→"能导出"；不叠限定词（"可能在部分情况下或许"），拿不准就实测，实测不了标 `[待确认]`。

## 三、常见问题写法

- 小标题用业务人员真实会问的大白话提问：✅"为什么我这单提交不了？" ❌"提交校验规则说明"。手册后期会被 AI 内化按口语提问召回，问题越像真人问的越准。
- 回答按「原因 → 解决办法」组织，多个原因逐条给解法，结尾说一句解决后是什么样。

## 四、配图

图是给读者定位用的，每张图都要回答"我现在该看屏幕哪里"。

- 每个操作序列至少三类图：**入口图**（在哪点，红框标注）、**过程图**（表单/弹窗）、**结果图**（系统反馈）。能合并的合并，不为凑数一步一图。
- 图注写在 Markdown 图片的 alt 位置：`![图 <章节号>-<序号>：<读者视角一句话>](images/xxx.png)`（"点右上角「新建」按钮"，不写"截取了新建按钮"）；正文提到某张图时说「如图 2-3」，被引用的图必须存在。
- 图片一律相对路径（`images/…`），与文档同级放 images 目录，任何 Markdown 编辑器打开都要能看到图。
- **每张图都要有红框**指出这一步该看哪、该点哪，没有红框的图不放。
- 图放进它对应的步骤条目里，做到一段文字一张图交错往下走。
- 弹窗、抽屉用局部截图；整页图只用于交代位置。
- 字段的界面表现（显隐、默认值）写进字段表说明列，字段表里不放图。
- 截图数据用演示数据，不出现真实客户敏感信息。

## 五、标记

- `[待确认]`：需要用户校正（不确定的业务逻辑、推测的字段含义、拿不准的例子）。
- `[待补充]`：需要后续积累（暂无内容的常见问题、注意事项）。
